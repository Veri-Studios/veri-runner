# Trajectory JSONL format

This is the file you download from a job's trajectory archive ("raw JSONL" on
the job page). One file per rollout, one JSON record per file, written by
`HarnessRunner._write_trajectory` in `veri_runner/harness_rollout.py`.

## Rollout record

| Field | Type | Meaning |
| --- | --- | --- |
| `rollout_id` | string | `s{policy_step}-t{task_index}-r{rollout_index}` |
| `policy_step` | int | Trainer global step whose policy generated this rollout |
| `task_index` | int | Index of the dataset task within the step |
| `rollout_index` | int | Which of the GRPO group members this rollout is |
| `status` | string | `completed`, `failed`, or `truncated` (harness timeout) |
| `reward` | float or null | Weighted sum of your reward function(s); null unless completed |
| `num_turns` | int | Number of captured model calls (spans) |
| `tokens_in` / `tokens_out` | int | Sum of prompt / completion token ids across spans |
| `task_input` | any | The dataset row's `prompt` column |
| `error` | string or null | Why the rollout failed (e.g. `template_drift: ...`, harness exit tail) |
| `spans` | list | One entry per model call, see below |
| `episode` | object or null | The rendered training episode, null when rejected |

## Span

One span per request your harness made to the policy endpoint, captured by
`veri_runner/trajectory_proxy.py`:

| Field | Type | Meaning |
| --- | --- | --- |
| `rollout_id` | string | Same as the parent record |
| `request_index` | int | Order of the call within the rollout (0-based) |
| `path` | string | `/v1/chat/completions`, `/v1/completions`, or `/v1/messages` |
| `request` | object | Your harness's request body, verbatim |
| `response` | object | The response body your harness received, verbatim |
| `prompt_token_ids` | list[int] or null | The server's own tokenization of the rendered prompt |
| `completion_token_ids` | list[int] or null | The server's sampled completion token ids |
| `completion_logprobs` | list[float] or null | Per-completion-token logprobs (best effort) |
| `started_at` / `duration_s` | float | Request timing |
| `token_fidelity` | string | `captured` (ids present) or `absent` (never trained on) |

## Episode

Produced by `render_episode` from the spans (delta tokenization, verl-style):

| Field | Type | Meaning |
| --- | --- | --- |
| `input_ids` | list[int] | One token stream for the whole trajectory |
| `loss_mask` | list[int] | 1 = trained (assistant completion tokens), 0 = masked (prompt, tool results, template) |
| `num_turns` | int | Spans consumed |
| `final_completion_text` | string | Last assistant message (what text-signature reward functions see) |
| `metadata.total_tokens` | int | `len(input_ids)` |
| `metadata.render_fallback` | string, optional | `last_turn` when strict prefix stitching failed and only the final span was trained (see below) |

## Rejection and fallback semantics

- Any span with `token_fidelity: "absent"` rejects the whole rollout
  (`error` starts with `template_drift:`); it is never trained on.
- Multi-turn stitching requires turn k's `prompt_token_ids` to extend turn
  k-1's `prompt_token_ids + completion_token_ids` exactly. If that fails (chat
  templates that rewrite prior turns, e.g. thinking models), the episode falls
  back to the final span only and is marked `render_fallback: "last_turn"`:
  token-exact but partial training signal.
- Failed/truncated rollouts still enter the GRPO batch as fully-masked
  single-token sentinels (reward 0, no gradient) so fixed-size groups stay
  aligned; see `build_rollout_batch` in `veri_runner/training_runtime.py`.

Worked examples: [`examples/rejected_trajectory_token_fidelity.jsonl`](../examples/rejected_trajectory_token_fidelity.jsonl)
and [`examples/template_drift_last_turn_fallback.jsonl`](../examples/template_drift_last_turn_fallback.jsonl)
(both generated by running the real capture/render code).
